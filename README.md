# รายงานสรุปภาพรวมและสถาปัตยกรรม — ME Coin Backoffice

> เอกสารนี้อธิบายภาพรวมและหลักการออกแบบด้านความปลอดภัยของระบบหลังบ้าน เพื่อใช้อ้างอิงและเผยแพร่ต่อสาธารณะ โดยไม่เปิดเผยซอร์สโค้ด ข้อมูลผู้ใช้ ค่าตั้งค่า ชื่อตัวแปรสภาพแวดล้อม ที่อยู่ของระบบ หรือรายละเอียดใดที่ช่วยให้เข้าถึงระบบได้

## 1. ภาพรวม

ME Coin Backoffice คือระบบหลังบ้านสำหรับดูแลผู้ใช้ กระเป๋าเงิน การชำระเงิน การอนุมัติ งานความเสี่ยง งานซัพพอร์ต การตรวจสอบย้อนหลัง และการตั้งค่าระบบ

ระบบแบบนี้มีผู้ใช้งานไม่มาก แต่ทุกคนถือสิทธิ์ที่แตะเงินของลูกค้าได้ การออกแบบจึงไม่ได้เริ่มจากคำถามว่าจะทำฟีเจอร์อะไร แต่เริ่มจากคำถามว่า **ถ้าบัญชีพนักงานหนึ่งบัญชีถูกยึด ความเสียหายจะหยุดที่ไหน**

## 2. หลักการออกแบบด้านความปลอดภัย

### 2.1 แยกบัญชีลูกค้ากับบัญชีพนักงานออกจากกันทั้งโครงสร้าง

ลูกค้าและพนักงานหลังบ้านไม่ได้อยู่ในชุดข้อมูลเดียวกันแล้วแยกด้วยคอลัมน์บอกบทบาท แต่แยกเป็นคนละชุดข้อมูลตั้งแต่ตัวบัญชี สิทธิ์ เซสชัน รหัสยืนยัน การตั้งรหัสผ่านใหม่ ไปจนถึงการแจ้งเตือน

เหตุผลคือการแยกด้วยคอลัมน์เดียวทำให้ความผิดพลาดในการเขียนเงื่อนไขเพียงจุดเดียว สามารถทำให้ขอบเขตข้อมูลสองฝั่งปนกันได้ ส่วนการแยกโครงสร้างทำให้ความผิดพลาดแบบนั้นกลายเป็นข้อผิดพลาดที่เห็นทันที ไม่ใช่ช่องโหว่ที่เงียบ

### 2.2 ยืนยันตัวตนสองชั้นทุกครั้งที่พนักงานเข้าสู่ระบบ

พนักงานหลังบ้านทุกระดับต้องยืนยันด้วยรหัสที่ส่งทางอีเมลทุกครั้งที่เข้าสู่ระบบ รหัสมีอายุจำกัดและจำกัดจำนวนครั้งที่กรอกผิดได้

### 2.3 ยืนยันซ้ำก่อนทำรายการที่มีความเสี่ยงสูง

การเข้าสู่ระบบสำเร็จไม่ได้แปลว่าทำได้ทุกอย่าง รายการที่มีความเสี่ยงสูงต้องยืนยันตัวตนซ้ำอีกครั้งก่อนดำเนินการ

### 2.4 รายการสำคัญต้องมีคนที่สองอนุมัติ

คำขอเพิ่มมูลค่าที่อ้างอิงหลักฐานการโอน ต้องให้พนักงานอีกคนเป็นผู้อนุมัติ ไม่สามารถทำจบได้ด้วยบัญชีเดียว

นี่คือมาตรการที่ตอบคำถามตั้งต้นของเอกสารนี้โดยตรง ต่อให้บัญชีพนักงานหนึ่งบัญชีถูกยึด ผู้โจมตีก็ยังทำรายการประเภทนี้ให้สำเร็จด้วยตัวคนเดียวไม่ได้

### 2.5 การเปลี่ยนสิทธิ์มีผลทันที

ระบบตรวจสถานะและสิทธิ์ของบัญชีจากฐานข้อมูลในทุกคำขอ การระงับสิทธิ์จึงมีผลกับเซสชันที่เปิดค้างอยู่ทันที ไม่ต้องรอให้โทเคนหมดอายุ

### 2.6 บัญชีใหม่เริ่มที่สถานะยังไม่ได้รับอนุมัติ

บัญชีพนักงานที่ลงทะเบียนเข้ามาใหม่จะยังไม่เห็นข้อมูลใดในระบบ จนกว่าผู้ดูแลระดับสูงสุดจะอนุมัติให้สิทธิ์

### 2.7 บันทึกตรวจสอบย้อนหลัง

การเปลี่ยนสิทธิ์และการกระทำสำคัญถูกบันทึกไว้ เพื่อให้ตอบได้เสมอว่าใครทำอะไรเมื่อไร

### 2.8 ฝั่งลูกค้าเก็บเฉพาะค่าที่ไม่ย้อนกลับได้

ข้อมูลยืนยันตัวตนของลูกค้าถูกเก็บเป็นค่าแฮช เพื่อใช้บังคับกติกาหนึ่งคนต่อหนึ่งบัญชี โดยไม่ต้องเก็บตัวเลขจริงไว้ในระบบ

## 3. สถาปัตยกรรม

- **API** เขียนด้วย Express และ TypeScript หน้าเว็บทุกหน้าดึงข้อมูลผ่าน API ไม่มีหน้าใดต่อฐานข้อมูลเอง
- **ฐานข้อมูล** MongoDB เข้าถึงผ่าน Prisma โดยมีแบบจำลองข้อมูลราว 45 ชุด
- **ชั้นป้องกันพื้นฐาน** ส่วนหัวความปลอดภัยของ HTTP, การจำกัดอัตราการเรียกที่เก็บสถานะไว้บน Redis เพื่อให้มีผลข้ามอินสแตนซ์ และการตรวจรูปร่างข้อมูลขาเข้าด้วย Schema
- **การชำระเงิน** เชื่อมกับผู้ให้บริการภายนอก โดยสถานะที่ยังไม่ได้รับการยืนยันจะไม่ถูกนับเป็นรายการสำเร็จ
- **บัญชีแยกประเภท** มีขั้นตอนตั้งยอดตั้งต้นของบัญชีสำรองก่อนเปิดระบบ เพื่อให้ยอดรวมตรวจสอบได้ตั้งแต่วันแรก

## 4. การส่งขึ้นใช้งาน

กระบวนการตรวจก่อนนำขึ้นใช้งานจริงเรียงเป็นชั้น และทุกชั้นต้องผ่านก่อนไปชั้นถัดไป

1. ยกบริการที่ระบบพึ่งพาขึ้นมาจริง แล้วติดตั้งโครงสร้างฐานข้อมูล
2. ทดสอบการทำงานร่วมกันกับฐานข้อมูลจริง ไม่ใช่ตัวจำลอง
3. สร้างหน้าเว็บสำหรับใช้งานจริง
4. สร้าง Container ด้วยไฟล์ชุดเดียวกับที่ใช้จริง เพื่อจับปัญหาที่เกิดเฉพาะใน Container
5. ตรวจช่องโหว่ของไลบรารีที่ใช้ตอนใช้งานจริง และหยุดทันทีเมื่อพบระดับสูงขึ้นไป
6. นำขึ้นใช้งานแบบ Blue-Green แล้ว **รอจนกว่าเวอร์ชันที่ขอจะขึ้นให้บริการจริง** ไม่ใช่จบที่การสั่งให้นำขึ้น

ป้ายกำกับรุ่นของ Container ถูกบังคับให้ไม่ซ้ำและเขียนทับไม่ได้ ป้ายหนึ่งจึงชี้ไปที่รุ่นเดียวตลอดไป ทำให้การถอยกลับได้ของชุดเดิมจริง
